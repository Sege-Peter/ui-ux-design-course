## Scoring Scale:
- **0 = No Problem:** Adheres to best practice.
- **1 = Cosmetic Issue:** Minor polish; does not impede task flow.
- **2 = Minor Usability Problem:** Users encounter friction but recover independently.
- **3 = Major Usability Problem:** Users fail or get severely delayed; high priority fix.
- **4 = Usability Catastrophe:** Product failure; imperatively blocking completion.

---

### 1. Visibility of System Status
*The design should always keep users informed about what is going on, through appropriate feedback within a reasonable time.*

- [ ] Does every button provide immediate visual feedback on click/tap (e.g. active state, ripple)?
- [ ] Are loading spinners or skeleton screens shown for asynchronous operations lasting >1 second?
- [ ] Are upload, download, or multi-step progress bars clear and informative?
- [ ] Is the user's current location within the navigation hierarchy clearly indicated?

### 2. Match Between System and the Real World
*The design should speak the users' language. Use words, phrases, and concepts familiar to the user, rather than internal jargon.*

- [ ] Is terminology intuitive to target users, avoiding technical error codes or database schema names?
- [ ] Do visual icons match real-world metaphors (e.g., trash can for delete, envelope for email)?
- [ ] Are dates, currencies, and numbers formatted according to the user's locale?

### 3. User Control and Freedom
*Users often perform actions by mistake. They need a clearly marked "emergency exit" to leave the unwanted action without having to go through an extended process.*

- [ ] Can users easily cancel, dismiss, or close modals and dialogs with a single click or Escape key?
- [ ] Is there an "Undo" capability for critical or destructive operations?
- [ ] Can users edit form inputs easily without losing previously entered data?

### 4. Consistency and Standards
*Users should not have to wonder whether different words, situations, or actions mean the same thing. Follow platform and industry conventions.*

- [ ] Are navigation items located in conventional positions (e.g. logo at top-left, cart at top-right)?
- [ ] Is terminology consistent across all screens (e.g., don't use "Log In" on one screen and "Sign In" on another)?
- [ ] Do all primary buttons share identical corner radius, elevation, and padding tokens?

### 5. Error Prevention
*Good error messages are important, but the best designs carefully prevent problems from occurring in the first place.*

- [ ] Are destructive actions (e.g. deleting an account or dataset) guarded by explicit confirmation dialogs?
- [ ] Do input fields use proper keyboards and masks (e.g., numeric keypad for phone numbers)?
- [ ] Are obvious formatting constraints shown upfront before submission (e.g. password rules)?

### 6. Recognition Rather Than Recall
*Minimize the user's memory load by making elements, actions, and options visible. The user should not have to remember information from one part of the interface to another.*

- [ ] Are search filters and active criteria visibly pinned on the results screen?
- [ ] Does the interface suggest recent searches or popular autocomplete queries?
- [ ] Are required form input fields explicitly marked rather than forcing the user to guess?

### 7. Flexibility and Efficiency of Use
*Accelerators—unseen by the novice user—may speed up the interaction for the expert user such that the design can cater to both inexperienced and experienced users.*

- [ ] Are keyboard shortcuts available for repetitive, high-frequency actions?
- [ ] Does the product support bulk actions (e.g. select all, multi-file upload)?
- [ ] Can experienced users customize or personalize their dashboard layout?

### 8. Aesthetic and Minimalist Design
*Interfaces should not contain information that is irrelevant or rarely needed. Every extra unit of information in an interface competes with the relevant units of information.*

- [ ] Does the screen adhere to the 60-30-10 color rule with ample negative space?
- [ ] Is secondary or rarely accessed information tucked into expandable drawers or disclosure widgets?
- [ ] Is visual clutter minimized to ensure the primary call-to-action stands out immediately?

### 9. Help Users Recognize, Diagnose, and Recover from Errors
*Error messages should be expressed in plain language (no error codes), precisely indicate the problem, and constructively suggest a solution.*

- [ ] Do error messages appear contextually right beside the invalid input rather than in an ambiguous global alert?
- [ ] Does the message explain *why* the error occurred and *how* to fix it?
- [ ] Does the interface preserve validly filled inputs after an error submission?

### 10. Help and Documentation
*It's best if the system doesn't need any additional explanation, but it may be necessary to provide documentation to help users complete their tasks.*

- [ ] Is help easily searchable and focused on the user's specific task?
- [ ] Are contextual tooltips provided for complex or unfamiliar concepts?
- [ ] Can users quickly reach human support if self-service troubleshooting fails?
